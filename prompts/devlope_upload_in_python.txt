# Role

Act as a Senior Python Backend Developer and Software Architect with extensive experience in developing REST APIs, file storage systems, Python Flask, and scalable backend applications.

Your task is to implement the first API of the File Upload Server using Python and Flask.

Read and understand the existing OpenAPI/Swagger specification before implementing anything.

The implementation must strictly follow the API contract defined in the Swagger document.

# 1. Project Objective

Develop the following REST API:

**POST /api/v1/files**

The API must allow clients to upload files to the server.

The server must:

1. Accept a file through a multipart/form-data request.
2. Validate the uploaded file size against a configurable maximum file-size limit.
3. Generate a unique UUID for every uploaded file.
4. Save the uploaded file in a configurable directory on the server.
5. Optionally encrypt the file if the client enables encryption.
6. Store file metadata in a file-based database.
7. Return the generated file ID and associated metadata in the API response.

Only implement the upload API for now.

Do not implement the list, delete, or download APIs.

However, design the application architecture so that these APIs can be added later without major modifications.

Use the following technologies:

# 3. API Specification

## Endpoint

POST /api/v1/files

## Request Content-Type

multipart/form-data

## Request Parameters

| Parameter | Type | Required | Default | Description |
|---|---|---|---|---|
| file | File | Yes | - | File to upload |
| encrypt | Boolean | No | false | Whether to encrypt the file before storing it |

## API Processing Flow

Implement the following processing sequence:

1. Receive the HTTP request.
2. Validate the request content type.
3. Validate that the file parameter exists.
4. Validate that the uploaded filename is not empty.
5. Validate the file size.
6. Generate a UUID for the uploaded file.
7. Generate a unique physical filename using the UUID.
8. If encryption is enabled, encrypt the file using AES-256-GCM.
9. Save the file in the configured storage directory.
10. Create the file metadata record.
11. Persist the metadata using the configured metadata repository.
12. Return HTTP 201 with the generated file ID and metadata.

Ensure that failures during file processing do not leave partially uploaded files or inconsistent metadata records.

# 4. File Storage Implementation

Implement a dedicated file storage module.

Requirements:

- The storage directory must be configurable.
- The server must create the storage directory automatically if it does not exist.
- The original filename must be stored as metadata.
- Never use the original filename directly as the physical storage filename.
- Generate physical filenames using UUIDs.
- Prevent path traversal attacks.
- Do not expose physical storage paths through the API.
- Avoid loading the entire uploaded file into memory unnecessarily.
- Use streaming or chunk-based processing wherever practical.
- Use temporary files during upload and encryption.
- Move the completed file atomically to its final storage location.

Suggested storage structure:

storage/
    files/
        a9e84e21-95d0-4c88-bcb2-52b99b4d8470

    temp/

The physical storage filename should not contain the original filename.

# 5. File Size Validation

The maximum file size must be configurable.

Introduce the following environment variable:

MAX_FILE_SIZE_MB=100

The default maximum file size should be 100 MB.

Requirements:

- Convert the configured MB value into bytes.
- Use Flask's MAX_CONTENT_LENGTH configuration.
- Implement application-level file size validation where necessary.
- Return HTTP 413 when the maximum allowed file size is exceeded.
- Do not hardcode the maximum file size in the upload implementation.
- Handle cases where the configuration value is invalid.
- Document the configuration parameter.

Important:

Flask/Werkzeug request-size limits can include multipart encoding overhead. Ensure that the application distinguishes the maximum permitted file size from the total HTTP request size when implementing validation.

# 6. Metadata Repository Architecture

The metadata storage layer must be modular and extensible.

Initially, implement a JSON-based file repository for storing metadata.

However, the architecture must support replacing the JSON repository with SQLite, PostgreSQL, or Redis in the future.

Do not implement metadata persistence directly inside the Flask route handler.

## Repository Interface

Create an abstract repository interface defining operations such as:

- save(metadata)
- get_by_id(file_id)
- delete(file_id)
- list_files(limit, offset)

Only implement save() for the current upload API if the other operations are not required yet.

Define the interface so that future implementations can provide the remaining operations.

## Initial Implementation

Implement:

JsonFileMetadataRepository

The repository must:

- Store metadata in a JSON file.
- Create the metadata file automatically if it does not exist.
- Persist records across application restarts.
- Prevent duplicate file IDs.
- Handle JSON serialization and deserialization safely.
- Handle filesystem errors.
- Avoid corrupting the metadata file if the process fails during a write.
- Use atomic file replacement when updating metadata.
- Implement basic locking or another suitable mechanism to prevent concurrent writes from corrupting metadata.

Keep the repository interface independent of Flask.

## Metadata Structure

Each uploaded file must have the following metadata:

{
    "id": "a9e84e21-95d0-4c88-bcb2-52b99b4d8470",
    "original_filename": "report.pdf",
    "stored_filename": "a9e84e21-95d0-4c88-bcb2-52b99b4d8470",
    "size_bytes": 1048576,
    "content_type": "application/pdf",
    "encrypted": true,
    "storage_path": "/internal/storage/path",
    "uploaded_at": "2026-11-27T12:30:00Z"
}

The storage_path must never be included in the API response.

The metadata repository must be replaceable without modifying the API controller or business logic.

# 7. Encryption Module

Implement encryption as a separate module.

Use AES-256-GCM authenticated encryption.

Requirements:

- Encryption must be optional.
- The default value of encrypt must be false.
- Encryption keys must be loaded from environment variables.
- Never hardcode encryption keys.
- Validate the encryption key configuration during application startup if encryption is enabled.
- Use a cryptographically secure random nonce.
- Persist the nonce and authentication tag in an appropriate format alongside the encrypted file or in associated metadata.
- Ensure that decryption information is available for future download API implementation.
- Never expose encryption keys in logs or API responses.
- Handle encryption failures safely.

For large files, do not assume that standard AES-GCM APIs support arbitrary chunk-based encryption while preserving a single authenticated message.

Select a secure, documented approach for streaming encryption, or impose a configurable maximum size appropriate to the selected implementation.

Do not invent a custom cryptographic algorithm.

Do not expose stack traces or internal exception details to clients.

Use appropriate logging for debugging and troubleshooting.
